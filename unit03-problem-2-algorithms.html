Submission D

Binary search works by maintaining an invariant: if the target is in the array at all, it is inside the current [lo, hi] window. Each step compares the middle element to the target and throws away the half that cannot contain it.

Throwing away that half is only justified if the array is sorted, because sortedness is what tells you that everything to the left of the middle is smaller and everything to the right is larger. On unsorted input that inference is false, so the half you discard may be the half holding your target. The algorithm still terminates and still returns an answer. The answer is just wrong. 
int[] a = {7, 2, 9, 1, 5};   // not sorted
binarySearch(a, 1);
// mid = a[2] = 9. Target 1 < 9, so we keep the left half {7, 2}.
// 1 isn't there, so we return -1.
// But 1 is in the array, at index 3, in the half we threw away.

Submission E

Binary search needs the array sorted, and it also needs the elements to be distinct. The reason is that at each step you compare the target against the middle element and decide which half to keep. If there are duplicates, the middle element can equal the target while other copies sit in both halves, so you cannot tell which half to keep and the search becomes ambiguous.

Binary search runs in O(log n), because the window halves on every step. Sorting first costs O(n log n) with a comparison sort. So if you only need one lookup, it is cheaper to scan the array once in O(n) than to sort it and then search. 
int[] a = {2, 5, 5, 5, 9};
binarySearch(a, 5);
// mid = a[2] = 5, so it matches and we return index 2.
// But which 5 did the student want? The algorithm can't say.

Submission F

Binary search is O(log n), and the reason is worth spelling out. Start with n candidates. After one comparison you have n/2 of them left, after two you have n/4, and in general after k comparisons you have n/2k. The search ends when that count reaches 1, which happens at k = log2(n). A million-element array takes about twenty comparisons and a billion-element array takes about thirty. Doubling the input adds a single step.

Sorting the input first costs O(n log n) with a comparison sort, which dominates the search itself. That is why you sort once and search many times, rather than sorting on every query. 
int lo = 0, hi = a.length - 1;
while (lo <= hi) {
    int mid = lo + (hi - lo) / 2;
    if (a[mid] == target) return mid;
    if (a[mid] < target) lo = mid + 1;
    else hi = mid - 1;
}
return -1;
