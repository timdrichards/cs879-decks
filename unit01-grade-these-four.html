Submission 2

JavaScript provides three variable declaration keywords, each with distinct scoping and mutability
characteristics.

`var` declarations are function-scoped and are hoisted to the top of their enclosing function,
initialized as `undefined`. `let` and `const` are block-scoped, meaning they are confined to the
nearest enclosing block, and are subject to the temporal dead zone, which prevents access prior to
declaration. `const` additionally prevents reassignment of the binding, though it does not render
the referenced value immutable.

A common bug arises when `var` is used within a loop that creates closures. Because `var` is
function-scoped, all closures share a single variable binding, causing each to observe the final
value after the loop completes. Using `let` creates a new binding per iteration, ensuring each
closure captures the expected value.

Selecting the appropriate declaration keyword is therefore essential for predictable behavior.

Submission 3

The three differ along two axes: scope and reassignability.

Scope — `var` is function-scoped, so it escapes blocks. `let` and `const` are block-scoped and stay
inside the nearest `{}`. Reassignability — `var` and `let` can be reassigned, `const` cannot,
though `const` only freezes the binding, not the object. `const arr = []` still permits
`arr.push(1)`.

The bug I actually hit was in the gallery lab. I built the thumbnail handlers in a `for (var i...)`
loop and every thumbnail opened the last image. All six handlers closed over the same `i`, which by
then was 6. Changing `var` to `let` gave each iteration its own binding and it worked immediately.

Since then I default to `const`, switch to `let` only when I know I'm reassigning, and never reach
for `var`. The restriction catches mistakes rather than causing them.

Submission 4

Scope is the main difference. `var` is scoped to the enclosing function; `let` and `const` are
scoped to the enclosing block. `const` also prevents reassignment of the binding itself, though the
value it points at can still be mutated — an object declared `const` can have its properties
changed.

The classic bug is the loop-closure problem. If you register callbacks inside a `for (var i = 0;
...)` loop, all of them share one `i` and see its final value. With `let`, each iteration binds a
fresh `i` and the callbacks behave as intended.

There is a related trap that bit me on the fetch exercise: `const` on a variable I was reassigning
inside a `.then()` threw a TypeError that I initially misread as a network failure, because the
error surfaced inside the promise chain rather than at the declaration.
